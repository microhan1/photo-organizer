# 실수 기록 (LESSONS)

이 저장소에서 실제로 생긴 문제를 모두 적는다. 새 문제가 생기면 같은 형식으로 **해당 절 맨 아래에 추가**하고, 재발 방지 테스트나 규칙을 반드시 함께 남긴다. 요약 규칙은 [CLAUDE.md](../CLAUDE.md)에 있다.

형제 저장소의 기록도 먼저 읽는다: [music-folder-organizer](https://github.com/microhan1/music-folder-organizer) `docs/LESSONS.md`(이 저장소의 `mover.py`·`undo.py`가 그쪽 것), [music-tag-filler](https://github.com/microhan1/music-tag-filler) `docs/LESSONS.md`. 그쪽에서 이미 겪은 문제(되돌리기 기록 없이 옮김, 재실행 때 번호가 늘어남, NFC/NFD, 읽기 전용 파일, tkinter pack 순서, 한글 글꼴, 잠금 화면 캡처, heredoc 백슬래시)는 처음부터 피하도록 설계했다. 아래는 이 저장소에서 새로 생긴 것만 적는다.

형식: 증상 → 원인 → 해결 → 재발 방지

## A. 제품 코드 버그

### A1. 설정 클래스의 필드 이름이 같은 이름의 모듈을 가림 (2026-10-06, 첫 실행 전 발견)
- 증상: `import prefs`가 `AttributeError: 'bool' object has no attribute 'DEFAULT_QUALITY'`로 실패
- 원인: `Prefs` 데이터클래스에 `convert: bool = False` 필드를 먼저 선언한 뒤 같은 클래스 본문에서 `convert.DEFAULT_QUALITY`(모듈)를 기본값으로 씀. 클래스 본문 안에서는 필드 이름이 모듈 이름을 가린다. `dedupe` 필드도 같은 문제
- 해결: `import convert as convert_mod`, `import dedupe as dedupe_mod`
- 재발 방지: 규칙 — **필드·변수 이름과 같은 이름의 모듈은 별칭으로 가져온다**. 모든 모듈을 import하는 시험(`test_i18n.py`의 키 검사)이 이를 잡는다

### A2. 긴 경로(`\\?\`)를 옮기기에만 적용하고 읽기에는 빠뜨림 (2026-10-06, 테스트 작성 중 발견)
- 증상: PRD "원본 경로가 이미 길면 `\\?\` 접두어로 접근"을 `mover.py`의 옮기기·지우기에만 넣었음. 스캔(`os.scandir`)·EXIF 읽기·변환·해시·썸네일은 일반 경로로 열어 260자가 넘는 폴더는 "읽을 수 없는 폴더"로 빠졌을 것
- 원인: 기능을 "파일을 바꾸는 곳"에서만 생각함. 파일을 **여는** 곳도 같은 제약을 받는다
- 해결: `longpath.py`의 `fs()`를 모든 파일 접근(열기·목록·이름 바꾸기·지우기)에 쓰고, 보여 주거나 기록하는 경로는 일반 형태로 둔다(스캔은 `\\?\` 형태의 `DirEntry.path`가 아니라 원래 폴더 경로에 이름을 붙여 경로를 만든다)
- 2026-10-06 음악 툴(music-folder-organizer)에 같은 문제가 있어 `longpath.py`를 옮겨 반영함(그쪽 LESSONS A24~A26). `longpath.py`는 두 저장소가 같은 파일: 한쪽을 고치면 다른 쪽도. 그쪽에서 `os.walk`가 긴 폴더를 조용히 건너뛴다는 것을 알게 되어 `longpath.walk()`가 추가됨(이 저장소의 스캔은 처음부터 `scandir`로 직접 걸어 영향 없음)
- 재발 방지: `test_formats.py`의 긴 경로 시험(스캔 → 정리 → 변환 → 되돌리기). 규칙 — **경로 제약은 파일을 여는 모든 곳에 적용되는지 `grep "open(\|listdir\|scandir\|Image.open"`으로 확인한다**

### A3. 사용자가 "이 사진 남기기"로 지정한 파일을 다시 중복으로 보냄 (2026-10-06, 시험이 잡음)

### A4. 완전히 같은 파일 중 원본 대신 `copy.jpg`를 남김 (2026-10-06, 시험이 잡음)

### A5. 고배율 화면에서 창이 PRD 크기의 2/3로 작아지고 글자만 커짐 (2026-10-06, 측정으로 발견)
- 증상: DPI 인식을 켠 뒤 `geometry("1100x760")`을 물리 픽셀로 줌. 이 PC(2880×1800, 150 %, `tk scaling` 2.0)에서는 창이 733×507 논리 크기로 보이고, 글꼴(포인트 단위)은 1.5배인데 여백·표 행 높이(픽셀 단위)는 그대로라 옵션이 들어갈 수 없음. 음악 툴도 같은 방식(1280×… 픽셀)
- 원인: PRD의 크기를 논리 크기가 아니라 물리 픽셀로 해석. 화면이 잠겨 스크린샷을 못 보던 중, 옵션 줄 폭을 재다 배율 값(`winfo_fpixels("1i")` = 144)을 보고 알게 됨
- 해결: `theme.set_scale()`/`px()` — 창 크기·최소 크기·여백·행 높이·드롭 영역 그림을 배율만큼 키움(화면보다 크게는 안 함)
- 재발 방지: 규칙 — **픽셀 상수는 `px()`를 거친다. 스크린샷은 실제 배율 화면에서 찍는다**(`tests/shots.py`는 앱과 같은 `size_window`를 씀). 음악 툴에도 같은 문제가 있음을 알려야 함

### A10. "정렬용 이름 바꾸기"와 `{source}` 폴더 규칙을 같이 쓰면 재실행마다 폴더가 바뀜
- 증상: 첫 실행에서 `band_20240121_19.jpg`(메신저) → `2019/Messengers/…/2019-07-01_080000_band_….jpg`. 두 번째 실행에서는 같은 파일이 `2019/Camera/…`로 또 이동. 스크린샷 이름도 `Other`로 바뀜
- 원인: 출처(`{source}`)를 파일명 패턴(`^band_`, `^Screenshot_` — 이름 맨 앞에 고정)으로 정하는데, 이름 바꾸기가 앞에 `2019-07-01_080000_`를 붙여 패턴이 더는 맞지 않음
- 해결: `patterns.strip_renamed()` — 이 프로그램이 붙인 접두어를 떼고 원래 이름으로 출처를 판정, 접두어의 날짜는 그 파일이 옮겨진 날짜로 읽음. `plan.renamed_stem()`은 접두어를 쌓지 않고 바꿈(날짜를 손으로 고치면 `2020-…_2019-…_이름`이 되던 것도 함께 막음)
- 재발 방지: `test_scenarios`(seed 4), `test_rename_option_survives_a_second_run_and_a_new_date`, `test_prefix_of_the_rename_option_is_understood_by_the_name_reader`. 규칙 — **프로그램이 이름을 바꾸는 기능은, 바꾼 이름을 다음 실행이 같은 방식으로 읽는지 재실행 시험으로 확인한다**

### A11. 폴더 연결(junction·심볼릭 링크)이 위로 되돌아가면 같은 사진을 여러 번 읽음
- 증상: `a/loop`이 상위 폴더를 가리키는 junction이면 스캔이 경로가 한계에 닿을 때까지 같은 파일을 반복해서 찾음(`IMG_A.jpg`가 한 장인데 여러 개로 나옴). 그대로 실행하면 같은 파일이 여러 경로로 계획에 들어감
- 원인: `DirEntry.is_dir(follow_symlinks=False)`는 junction에 대해 True라 따라 들어감
- 해결: 하위 폴더가 `is_symlink()`나 `is_junction()`이면 들어가지 않음(원드라이브 폴더 자리표시자는 해당 없음). 사용자가 연결의 실제 폴더를 직접 고르면 됨
- 재발 방지: `test_folder_junction_loop_does_not_hang_the_scan`, `test_symlink_to_a_folder_is_not_followed`

### A12. 언어를 바꾸고 다시 실행하면 "날짜 없음" 폴더의 파일이 새 이름 폴더로 이동
- 증상: 한국어로 정리한 `날짜 없음/`의 파일이, 영어로 바꾼 뒤 계획에서는 `No Date/`로 옮겨짐(PRD: 폴더 이름은 언어 파일에서)
- 원인: 새 폴더 이름만 현재 언어로 계산하고, 이미 있는 다른 언어 이름의 폴더를 알아보지 않음. 중복·원본 HEIC 폴더는 스캔에서 모든 언어 이름을 건너뛰어 괜찮았음
- 해결: 사진이 대상 폴더 바로 아래의 "날짜 없음" 폴더(어느 언어 이름이든)에 이미 있으면 그 폴더가 제자리(`_nodate_folder_in_place`)
- 재발 방지: `test_switching_language_does_not_reshuffle_special_folders`(ko→en, en→ja, zh-CN→ko)

### A13. 같은 복사를 다시 실행하면 이미 복사한 사진이 `_중복`에 쌓임
- 증상: 복사 모드로 `원본 → 대상` 정리 뒤 같은 명령을 다시 실행하면, 대상에 이미 같은 내용의 사본이 있어서 원본 파일이 "중복"으로 판정되어 `대상/_중복/`으로 또 복사됨. 번호가 붙은 이름(`x (2).jpg`)도 같은 식으로 늘어남
- 원인: "같은 이름·같은 내용의 파일이 자리에 있다"는 판정이 이동 모드의 의미(원본이 이미 정리된 파일의 중복)만 알고, 복사 모드에서는 "전에 만든 사본"이라는 뜻일 수 있음을 몰랐음
- 해결: 복사 모드에서 이 사진의 모든 파일이 이름·바이트까지 같은 사본으로, 이번 스캔에 들어 있지 않은 파일로 이미 대상에 있으면 `Item.present`(할 일 없음, "변경 없음")로 처리. `x`, `x (2)`… 순서로 디스크에 있는 이름까지 따라가며 확인
- 재발 방지: `test_copy_then_copy_again_does_not_pile_up_duplicates`

### A14. "HEIC 짝의 JPG를 중복으로"와 "HEIC → JPG 변환"을 같이 켜면 재실행마다 변환이 또 나옴
- 증상: 첫 실행에서 짝의 JPG는 `_중복`으로 가고 HEIC는 (JPG가 있어 보여) 변환하지 않음. 두 번째 실행에서는 홀로 남은 HEIC가 변환 대상이 됨. 변환하면 그 JPG를 중복 옵션이 또 치워 버리는 모순
- 해결: 두 옵션이 같이 켜지면 변환을 쓰지 않음(`prefs.options`; "변환만" 모드는 중복을 보지 않으므로 영향 없음). 설정 문구와 화면에도 알림
- 재발 방지: `test_scenarios`(seed 18). 규칙 — **서로 모순되는 옵션 조합은 허용하지 않거나 한쪽이 이긴다고 정하고, 조합을 무작위로 섞는 시험으로 찾는다**

### A15. `{ext}` 폴더 규칙 + 변환 + "원본 HEIC 옮기기": 홀로 남은 JPG가 재실행마다 다른 폴더로 이동
- 증상: 규칙 `by-ext/{ext}/{yyyy}`로 HEIC를 변환하며 원본을 `_원본HEIC`로 옮기면, 첫 실행의 JPG는 HEIC와 같은 `by-ext/heic/`에 놓이고, 두 번째 실행에서는 홀로 남은 JPG(와 라이브 포토 MOV)가 `by-ext/jpg/`로 또 이동
- 원인: 폴더 이름의 `{ext}`를 짝의 대표 파일(HEIC)의 확장자로 정했는데, 대표가 떠나면 JPG가 대표가 됨
- 해결: 변환하고 원본을 옮기는 경우 처음부터 `{ext}`는 `jpg`(그 JPG가 앞으로 사진이므로)
- 재발 방지: `test_ext_pattern_with_convert_and_moved_originals_is_stable`

### A16. "JPG를 중복으로" 옵션: 떠날 JPG의 날짜가 짝(HEIC)의 폴더를 정함
- 증상: HEIC(EXIF 없음) + JPG(EXIF 2024) + MOV(2020)가 있으면 첫 실행은 JPG의 날짜로 `2024/…`에 두고, JPG가 `_중복`으로 간 뒤 두 번째 실행은 MOV의 날짜로 `2020/…`으로 이동
- 원인: 짝의 날짜를 "대표에 없으면 짝에서 빌림"으로 정할 때 곧 떠날 JPG도 후보였음. 떠난 뒤에는 그 근거가 사라짐
- 해결: 이 옵션이 켜져 있으면 HEIC·RAW 대표의 날짜 근거에서 JPG를 처음부터 뺌
- 재발 방지: `test_the_date_of_a_pair_does_not_come_from_the_jpg_that_leaves_as_duplicate`. 규칙 — **"다음 실행에 남아 있는 파일만으로도 같은 결정이 나와야 한다": 이번 실행에서 사라질 파일을 결정의 근거로 쓰지 않는다** (A10·A15·A16 모두 같은 뿌리: 실행이 만든 변화가 다음 실행의 입력을 바꿈)
