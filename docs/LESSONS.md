# 실수 기록 (LESSONS)

이 저장소에서 실제로 생긴 문제를 모두 적는다. 새 문제가 생기면 같은 형식으로 **해당 절 맨 아래에 추가**하고, 재발 방지 테스트나 규칙을 반드시 함께 남긴다. 요약 규칙은 [CLAUDE.md](../CLAUDE.md)에 있다.

형제 저장소의 기록도 먼저 읽는다: [music-folder-organizer](https://github.com/microhan1/music-folder-organizer) `docs/LESSONS.md`(이 저장소의 `mover.py`·`undo.py`가 그쪽 것), [music-tag-filler](https://github.com/microhan1/music-tag-filler) `docs/LESSONS.md`. 그쪽에서 이미 겪은 문제(되돌리기 기록 없이 옮김, 재실행 때 번호가 늘어남, NFC/NFD, 읽기 전용 파일, tkinter pack 순서, 한글 글꼴, 잠금 화면 캡처, heredoc 백슬래시)는 처음부터 피하도록 설계했다. 아래는 이 저장소에서 새로 생긴 것만 적는다.

형식: 증상 → 원인 → 해결 → 재발 방지

## A. 제품 코드 버그

### A1. 설정 클래스의 필드 이름이 같은 이름의 모듈을 가림 (2026-10-06, 첫 실행 전 발견)
- 증상: `import prefs`가 `AttributeError: 'bool' object has no attribute 'DEFAULT_QUALITY'`로 실패
- 원인: `Prefs` 데이터클래스에 `convert: bool = False` 필드를 먼저 선언한 뒤 같은 클래스 본문에서 `convert.DEFAULT_QUALITY`(모듈)를 기본값으로 씀. 클래스 본문 안에서는 필드 이름이 모듈 이름을 가린다. `dedupe` 필드도 같은 문제
- 해결: `import convert as convert_mod`, `import dedupe as dedupe_mod`
- 재발 방지: 규칙 — **필드·변수 이름과 같은 이름의 모듈은 별칭으로 가져온다**. 모든 모듈을 import하는 시험(`test_i18n.py`의 키 검사)이 이를 잡는다

### A2. 긴 경로(`\\?\`)를 옮기기에만 적용하고 읽기에는 빠뜨림 (2026-10-06, 테스트 작성 중 발견)
- 증상: PRD "원본 경로가 이미 길면 `\\?\` 접두어로 접근"을 `mover.py`의 옮기기·지우기에만 넣었음. 스캔(`os.scandir`)·EXIF 읽기·변환·해시·썸네일은 일반 경로로 열어 260자가 넘는 폴더는 "읽을 수 없는 폴더"로 빠졌을 것
- 원인: 기능을 "파일을 바꾸는 곳"에서만 생각함. 파일을 **여는** 곳도 같은 제약을 받는다
- 해결: `longpath.py`의 `fs()`를 모든 파일 접근(열기·목록·이름 바꾸기·지우기)에 쓰고, 보여 주거나 기록하는 경로는 일반 형태로 둔다(스캔은 `\\?\` 형태의 `DirEntry.path`가 아니라 원래 폴더 경로에 이름을 붙여 경로를 만든다)
- 2026-10-06 음악 툴(music-folder-organizer)에 같은 문제가 있어 `longpath.py`를 옮겨 반영함(그쪽 LESSONS A24~A26). `longpath.py`는 두 저장소가 같은 파일: 한쪽을 고치면 다른 쪽도. 그쪽에서 `os.walk`가 긴 폴더를 조용히 건너뛴다는 것을 알게 되어 `longpath.walk()`가 추가됨(이 저장소의 스캔은 처음부터 `scandir`로 직접 걸어 영향 없음)
- 재발 방지: `test_formats.py`의 긴 경로 시험(스캔 → 정리 → 변환 → 되돌리기). 규칙 — **경로 제약은 파일을 여는 모든 곳에 적용되는지 `grep "open(\|listdir\|scandir\|Image.open"`으로 확인한다**

### A3. 사용자가 "이 사진 남기기"로 지정한 파일을 다시 중복으로 보냄 (2026-10-06, 시험이 잡음)
- 증상: 완전히 같은 두 파일 중 하나를 사용자가 "남기기"로 바꿔도, 새 경로를 정하는 단계에서 같은 이름·같은 내용 파일을 만나 `_중복`으로 다시 보냄
- 원인: 중복 판정이 두 곳(① `dedupe.find_exact` ② `plan._same_content` 이름 충돌 검사)에 있는데 사용자 지정은 ①에만 반영
- 해결: `Item.keep`(사용자가 남기기로 함)이면 ②도 건너뛰고 번호를 붙여 둘 다 남김
- 재발 방지: `test_exact_duplicate_kept_by_hand_is_not_moved`. 규칙 — **같은 판정이 여러 곳에 있으면 사용자 지정이 그 모든 곳에 닿는지 `grep`으로 확인한다**(음악 툴 A21과 같은 종류)

### A4. 완전히 같은 파일 중 원본 대신 `copy.jpg`를 남김 (2026-10-06, 시험이 잡음)
- 증상: `camera/IMG_0001.jpg`와 `chat/copy.jpg`가 같으면 `IMG_0001.jpg`가 중복으로 감
- 원인: 남길 것을 정하는 순서에 "경로가 짧은 것"만 있었음
- 해결: "복사본처럼 보이는 이름(`copy`, `- Copy`, `(2)`, `복사본`, `コピー`, `副本`)은 뒤로"를 경로 길이보다 앞에 둠
- 재발 방지: `test_identical_files_one_stays_kakao_copy_leaves`. 기대값은 짐작이 아니라 `_keep_order` 규칙을 따라 계산해서 썼다(음악 툴 C4)

### A5. 고배율 화면에서 창이 PRD 크기의 2/3로 작아지고 글자만 커짐 (2026-10-06, 측정으로 발견)
- 증상: DPI 인식을 켠 뒤 `geometry("1100x760")`을 물리 픽셀로 줌. 이 PC(2880×1800, 150 %, `tk scaling` 2.0)에서는 창이 733×507 논리 크기로 보이고, 글꼴(포인트 단위)은 1.5배인데 여백·표 행 높이(픽셀 단위)는 그대로라 옵션이 들어갈 수 없음. 음악 툴도 같은 방식(1280×… 픽셀)
- 원인: PRD의 크기를 논리 크기가 아니라 물리 픽셀로 해석. 화면이 잠겨 스크린샷을 못 보던 중, 옵션 줄 폭을 재다 배율 값(`winfo_fpixels("1i")` = 144)을 보고 알게 됨
- 해결: `theme.set_scale()`/`px()` — 창 크기·최소 크기·여백·행 높이·드롭 영역 그림을 배율만큼 키움(화면보다 크게는 안 함)
- 재발 방지: 규칙 — **픽셀 상수는 `px()`를 거친다. 스크린샷은 실제 배율 화면에서 찍는다**(`tests/shots.py`는 앱과 같은 `size_window`를 씀). 음악 툴에도 같은 문제가 있음을 알려야 함

### A6. 옵션 한 줄이 최소 폭에 들어가지 않음 (2026-10-06, GUI 시험이 잡음)

- 해결: PRD 규칙("안 들어가면 설정으로")에 따라 "변환만"은 폴더 규칙 목록의 마지막 항목으로, 대상 폴더는 "대상 폴더: 이름" 버튼 하나로. 영어 891/928
- 재발 방지: `test_every_control_fits_in_every_language`(4개 언어 × 기본·최소 크기, 위젯이 창 안에 있고 요청 폭보다 좁지 않은지)

### A7. 하단 요약이 두 줄이 되면 실행 버튼이 우하단에서 떠오름 (2026-10-06, 시험이 잡음)

### A8. 창 크기를 바꾸면 창이 멈춤 (2026-10-06, 150 % 화면 스크린샷에서 발견)
- 증상: 최소 크기로 줄이자 프로그램이 응답 없음(스크린샷 스크립트가 시간 초과)
- 원인: 하단 요약의 "수정 시각 사용" 토글 위치를 정할 때, 토글이 숫자 줄 안에 있으면 그 줄 폭에 토글이 이미 들어 있는데 토글 폭을 또 더함 → "안 들어감" → 둘째 줄로 → 줄이 좁아져 "들어감" → 다시 첫 줄로… `<Configure>` 안에서 끝없이 반복. 배율 1의 시험에서는 경계에 걸리지 않아 통과

- 재발 방지: `test_summary_reflow_settles_at_every_width`(최소~기본 폭을 6px씩 바꾸며 배치가 뒤집히지 않는지), `mutate_check.py`에 옛 계산을 넣은 변이(창이 멈춰 시간 초과 = 잡힘). 규칙 — **크기에 따라 배치를 바꾸는 코드는, 그 결정에 쓰는 값이 배치 결과에 따라 달라지지 않게 한다**

### A9. 10만 장이 2분 목표를 넘음 (2026-10-06, `PHOTO_PERF_100K=1` 시험이 잡음)
- 증상: 새로 만든 10만 파일 폴더에서 스캔+계획 307초(1차), 같은 폴더를 다시 읽으면 124초 → 고친 뒤 데워진 상태 약 40초
- 원인: ① 묶음·날짜 계산을 중복 찾기용과 계획용으로 두 번 함 ② 표준 EXIF 날짜까지 `strptime`(20만 번) ③ 계획 안에서 이미 절대 경로인 경로에 `abspath`(190만 번) ④ 처음 여는 파일은 디스크·백신 대기가 대부분인데 한 스레드로 하나씩 엶
- 해결: `build(grouped=)`로 재사용, 표준 형식은 직접 잘라 파싱, 계획 전용 `_tkey`, 날짜별 폴더 이름 캐시, `Item.moves` 캐시, 스캔 읽기를 스레드 8개(순서 유지, 256개마다 취소·진행 확인), `Meta`에 `slots`
- 재발 방지: 성능은 **처음 여는(차가운) 폴더**로 잰다 — 같은 폴더를 두 번째 재면 몇 배 빠르게 나와 속는다. 단계별 시간을 먼저 찍고(추측 금지), 고친 뒤 같은 조건으로 다시 잰다

- C10. 시험 중 `cd tests`로 들어가 세션 작업 폴더가 바뀜(형제 저장소 spread-split "cwd 때문에 폴더 삭제 실패"와 같은 함정) → 명령은 절대 경로로, `cd`하지 않는다

## D. 작업 방식 실수 (도구·환경)

- D1. 첫 GUI 스크린샷이 완전히 검게 나옴 → `WindowFromPoint`가 `LockScreenBackstopFrame`: PC가 잠겨 있었다(형제 저장소 spread-split·music-folder-organizer D9와 같은 일). 앱을 의심하기 전에 화면 상태를 먼저 확인하는 순서가 통했다. 잠긴 동안은 위젯 배치 수치 시험으로 대신하고, 실제 스크린샷은 잠금이 풀린 뒤 찍는다
- D2. 여러 파일의 import를 한 번에 고치려고 heredoc 파이썬 안에 `\n`이 든 치환을 씀 — 형제 저장소에서 네 번 재발한 "백슬래시가 든 수정은 Edit 도구로" 규칙 위반. 이번에는 `assert`로 일치를 확인해 결과는 맞았지만 우연이다 → 백슬래시가 하나라도 든 수정은 예외 없이 Edit 도구로
- D3. **음악 툴 D18 재발**: D: 저장소에서 C: 스크래치패드의 측정 스크립트에 `sed -i`를 썼다가 "Invalid cross-device link"로 실패(파일은 그대로, 그 뒤 명령이 옛 스크립트로 돌아 측정값 일부가 옛 코드 기준이 됨). 메모리에 적어 둔 규칙을 명령을 쓰는 순간 확인하지 않음 → 스크래치패드 파일 수정은 Edit 도구로만. `;`로 이어 붙인 다음 명령은 앞 명령이 실패해도 돈다는 것도 기억(검증 명령은 `&&`로)
- D2 **재발 (같은 날, PRD 부록)**: 문서 끝에 긴 글을 붙이려고 `cat >> 파일 <<'EOF'`를 씀 → 본문의 `\\?\`가 `\?\`로 바뀜. 따옴표 친 heredoc도 이 도구에서는 백슬래시를 지킨다는 보장이 없다(형제 저장소 ebook-cover-maker 메모와 같음). 바로 grep으로 확인해 Edit로 고침 → 규칙을 **코드뿐 아니라 모든 글**로 넓힘: 백슬래시가 든 글은 Write/Edit 도구로만 쓰고, 쓴 뒤 grep으로 확인
- D5. 스크린샷 스크립트가 두 번째 장에서 멈췄는데 `... | tail` 뒤의 `echo $?`가 0이라 "정상 종료"로 착각함 → 파이프의 종료 코드는 마지막 명령(`tail`)의 것. 출력을 파일로 보내고 `$?`를 바로 읽자 124(시간 초과)였고, 원인은 A8(창이 멈춤). 형제 저장소 PDF-To-Epub 메모에도 있는 함정 → 성공 여부를 볼 명령은 파이프에 넣지 않는다
- D6. 화면이 잠긴 동안 `tests/shots.py`가 잠금 화면을 찍고도 "saved"라고 함(D1 재발) → 찍기 전에 `WindowFromPoint` 클래스가 `LockScreenBackstopFrame`이면 종료 코드 3으로 멈추게 함
- D7. exe 연기 시험에서 `Start-Process`로 받은 PID의 창 제목이 비어 있었고, 그 PID를 끝냈는데 창이 남음 → onefile exe는 압축을 푸는 부모와 창을 띄우는 자식, 두 프로세스다. 확인은 `Get-Process photo-organizer`로 이름·시작 시각을 보고, 내가 띄운 시각 이후의 것만 닫는다
- D8. 창 모드 exe는 콘솔이 없어 CLI 인자를 줘도 창이 열림 → 얼린 exe 안의 작업 프로세스(HEIC 변환) 확인은 같은 코드로 `--console` 빌드를 `build\console-check`에 따로 만들어 CLI로 돌리고 지운다(5장 변환·되돌리기 정상, 남은 프로세스 0)
- D9. 다른 저장소에서 파일을 복사해 쓸 때 내용을 읽지 않음: 음악 툴의 `LICENSE`에는 이 프로젝트에 없는 `fpcalc.exe`(Chromaprint) 안내가 붙어 있었음. 그대로 올렸다가 GitHub가 MIT로 인식하지 못하고 "Other"로 표시해 발견(음악 툴 두 저장소도 같은 표시) → 표준 MIT 본문으로 교체. 규칙: **복사한 파일은 쓰기 전에 읽고, 그 프로젝트에 맞는지 확인한다. 공개 저장소는 올린 뒤 `gh repo view --json licenseInfo,repositoryTopics`로 인식 결과를 확인한다**
- D4. 성능 시험 데이터가 모든 파일을 같은 크기로 만들어 "완전 중복 찾기 9.5초(중복 0개)"로 보임 → 실제 원인(파일 열기 비용 약 1ms/개)은 맞았지만, 측정 데이터가 현실과 다르다는 점을 같이 적어 둔다. 스캔에서 한 번 열 때 앞 64KB 해시를 만들어 두어 해결(9.5초 → 0.008초)
